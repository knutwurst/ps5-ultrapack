────────────────────────────────────────────────────────────────────────
  v2.2.2  (current)
────────────────────────────────────────────────────────────────────────

FIXES

  - The app could quit on the spot when a folder or file chooser opened:
    macOS attached it to the main window as a sheet and ended the app
    when it refused that sheet. Choosers and messages now open as
    windows of their own.
  - After such a crash the running job kept going without the app,
    writing to the drive for nobody, and a restarted app ran the same
    job again. A job now ends together with the app.
  - A PS4 or Organize job from an archive showed a quarter of the
    unpack in the queue (17 % while the unpack stood at 71 %) and then
    jumped to the end. The archive is unpacked on the output drive and
    then only renamed into the library, so the queue bar now follows
    the unpack. When a copy to another drive follows, the unpack counts
    for half.
  - Such a job no longer asks for free space on the temp drive, which
    it never uses; it needs the space once, on the output drive. Its
    details say where it unpacks and what it needs there.
  - A PS4 game package with its update merged in got the game's version
    (v01.00): such a package keeps the game's version as its app version
    and states the update's in its master version, which an ordinary game
    uses for its own revision. The master version now counts when it is
    the higher one and the package's name, its folder or the archive it
    came in states that same version, e.g. '(v1.71)'.
  - While an archive is unpacked, Speed, Elapsed and Left are filled in.
  - A waiting job's details show where it will run: where the archive
    is unpacked, which drive builds the image (an extra temp drive such
    as a second SSD included), where the result goes, and what each of
    these drives needs and has free. They used to name the temp folder
    from Settings even when the job would use another drive.
  - The details pane belongs to the job you selected. Its progress
    block shows only while that job runs; a waiting job no longer shows
    another job's bar. When the next job starts, the list and the
    details move on to it only if you were watching the running job;
    a job you picked yourself stays picked.

────────────────────────────────────────────────────────────────────────
  v2.2.1
────────────────────────────────────────────────────────────────────────

ORGANIZE SORTS A FOLDER IN PLACE

  - Organize is now a view of the main window. Pick a folder (it starts
    with your output folder), and the app reads every game folder,
    .ffpfsc, .ffpfs, .exfat, .ffpkg, PS5 and PS4 .pkg and archive in it,
    at any depth, and shows where each one belongs: old name, new name,
    a checkbox each. Apply renames them; nothing is copied, so a whole
    drive is sorted in seconds.
  - Each game gets one title folder directly in the chosen folder,
    '<Title> [PPSA12345] [v01.300.000]', named after the newest version
    it holds. Images and packages inside get the names Auto-organize
    gives a new build; an unpacked game moves in as
    '<Title> [PPSA12345] [v01.000.000]'; PS4 packages follow the PS4
    layout with UPDATE, DLC and 'DLC Pack'.
  - Archives keep their file names, because the parts of a set must.
    A folder that holds one game's archives is renamed instead; a folder
    with several games' archives is split into one folder per game.
    When the app cannot tell which archive belongs to which game,
    nothing in that folder moves.
  - Notes, pictures and DLC folders next to a game move with it. In a
    folder shared by several games, they move only when their name
    names one of the games.
  - Rows that stay say why: the game could not be read, it is unclear
    whose archives these are, or two files would end up with the same
    name.
  - Undo last organize moves everything back where it was.
  - '._' files never show up in the list, and none are left behind
    after Apply or Undo, even on an exFAT drive ejected right away.
    Folders that Apply leaves empty are removed.

ORGANIZE AS A JOB OUTPUT

  - Add job has a fifth output next to Folder, .ffpfs, .ffpfsc and .pkg:
    Organize. The source goes into your library in the format it already
    has, under its library name, without being rebuilt. An archive is
    unpacked and what it holds goes over in its own format.
  - An existing title folder is joined, and its version tag goes up
    when the new item is newer.
  - The After-job rule decides between copy and move, as for every
    other job.

PS4 PACKAGES

  - A PS4 package (.pkg) in an archive, in a folder or on its own is
    recognised and copied into your library the way it is laid out:
    '<Title> [CUSA12345] [v01.07]' with the game, 'UPDATE [v01.07]' and
    '<Title> DLC <name>' inside; from four DLCs on they go into
    'DLC Pack'. A DLC carries the version of the game it came with.
  - When the output already holds the title's folder, the packages go
    into it, and a single DLC takes that folder's version and its
    'DLC Pack'. A newer game or update raises the folder's version
    ('[v01.00]' becomes '[v01.04]'), so the folder always shows the
    newest version it holds; a DLC never changes it.
  - Your Settings rule for outputs that are already there applies to
    every package of a set: skip, keep both or overwrite. Ask behaves
    like skip inside a running job.
  - Look inside lists a PS4 package and extracts single files or
    folders; Unpack writes its files to a folder. Both need a fake
    package; any other package is recognised and sorted, but its
    content cannot be read.
  - An archive of PS4 packages is recognised as such the moment you add
    it: the job is named from the first package, the editor offers the
    library only, and the PS5 options are hidden. A single PS4 package
    offers the library or an unpacked folder.
  - PS5 packages and images work exactly as before.

NO '._' FILES ON AN EXFAT DRIVE, EVEN WHEN YOU EJECT RIGHT AWAY

  - macOS tags every file the app writes with a provenance attribute.
    On an exFAT drive that attribute is stored as a '._' file next to
    the output. macOS removes it a few seconds later, but when the
    drive was ejected before that, it stayed. Every finished job now
    removes these files itself: next to a .ffpfsc, .ffpfs or .pkg,
    inside an unpacked folder, beside the extras copied next to the
    output, and in a PS4 title folder. Nothing else in your library is
    touched.

ALSO

  - The up and down arrow keys move the selection in the queue instead
    of moving the job; Shift extends the selection. Drag and drop and
    Move up / Move down in the context menu still move a job.
  - The game's picture in the job details stays. It used to vanish when
    you picked another job: after a restart every job lost it, and a
    job from an archive lost it once its unpacked copy was gone. The
    picture is now read when the job is added, straight from the
    archive (ZIP, and RAR or 7z that are not solid), the .ffpfsc or
    .ffpfs, or the PS5 or PS4 .pkg, and kept by the app. It is also
    larger.
  - An archive whose game cannot be read before it is unpacked (an image
    or a solid set inside) is named from the folder it sits in when that
    folder carries the title id and a name, until the real name is read
    after unpacking.

  v2.2.0
────────────────────────────────────────────────────────────────────────

A .PKG IS BUILT ON ALL CORES

  - Kraken now runs on every core of the Mac instead of one. On a 1 GB
    test game the package took 9 seconds instead of 40, and the result
    is the same file byte for byte, whatever the core count. The CPU
    cores setting applies to .pkg jobs too; 0 means all cores.
  - The package tool had been held to one core since its first release
    because it crashed with more. The cause was found and fixed: not the
    compressor, but the way the tool itself was packaged. The tool is
    now 82 MB instead of 38.
  - Reading a .pkg uses every core as well: unpacking one and Look inside
    no longer wait on a single thread.

BUILDING A .PKG: NO SECOND COPY OF THE GAME, NO HARD LINKS

  - A .pkg built from an image the app unpacked itself (a .ffpfsc,
    .ffpfs, .exfat or .pkg source) is now built right in that unpacked
    copy. Until now the package tool made one more copy of the whole game
    first; on an exFAT drive a real one: for a big game 149 GB and a
    quarter of an hour, with nothing on the progress bar.
  - A .pkg built from your own game folder still works on a copy, so the
    folder stays as it is, and that copy now shows its progress ("staging
    copy", 30 to 45 % of the job).
  - The package tool never uses hard links any more, on any drive. A
    change made for the package (signing, a dropped PlayGo file, the
    rewritten param.json) can no longer reach the source through a link.
  - A .ffpfsc or .ffpfs is unpacked in one pass, straight into files:
    the inner image is no longer written to the disk first. For a big
    game that is one copy of the game less on the temp drive and a
    quarter of an hour saved.
  - While a .pkg is built from the app's own unpacked copy (an image, an
    archive the app unpacked, a patched or backported game), each file
    is removed as soon as the package holds it: the unpacked game shrinks
    while the package grows instead of both sitting side by side. A
    build that fails is unpacked again on Retry.

A KRAKEN LEVEL SLIDER FOR .PKG, AND A SAFE CHECK OF THE FINISHED PACKAGE

  - The .pkg compression is a slider from -4 to 9 instead of "normal" and
    "fast", in the job dialog and in Settings, next to the zlib slider for
    .ffpfsc. The slider says what each step buys. Measured on a 1 GB game:
    -4 to -1 are the fastest and about 2 % larger; 0 to 5 cost a tenth
    more time and are 0.3 % larger than 7; 7 to 9 take 4 to 10 times as
    long for that last 0.3 %. 0 is the new default; a remembered "normal"
    or "fast" moves to it once.
  - The check of the finished .pkg reads the package in place: the file
    table of the inner image, then eboot.bin alone. Until now it unpacked
    the whole game into the temp folder to prove the image decodes; for
    a big game that was a second copy of the game and an hour at "Verify
    0 %". The check now reports its steps on the bar and keeps the few
    metadata files it lifts in the app's own temp folder.

A .PKG SHOWS ITS REAL PROGRESS, SPEED AND TIME LEFT

  - While Kraken runs, the bar now moves with the bytes done, and Speed
    and Left are filled in: the backend adds up the files the package
    already holds and the part of the file being packed. Until now the
    bar sat at 99 % for the whole pass and both fields showed a dash.
  - The outer-image pass that follows reports its percentage, speed and
    time left the same way; before, it stood at 0 % until it was done.
  - The progress bands of a .pkg job were re-weighted from a full-size
    run.

  v2.1.1

PAUSE AFTER THE RUNNING JOB

  - Start, Pause and Stop share one place in the queue header. Idle it
    is Start; when the queue runs it turns into Pause (orange) and Stop
    (red) side by side, with a short crossfade, and nothing beside it
    moves. With Reduce motion on in macOS it switches without the fade.
  - Pause (also in the menu: Pause After This Job) lets the running job
    finish completely, unpacking, building and what happens after it
    included, then the queue stops before the next job. The jobs left
    stay queued; Start runs them.
  - Until the job is done, Pause stays lit in orange and the progress
    line at the foot turns orange ("pauses after this job"); a second
    click takes the pause back.
  - A pause is not the end of the queue: no sleep, no quit, no summary.
    With notifications on, a banner says how many jobs are left. When
    the paused job was the last one, the queue ends as usual.
  - Stop still cancels the running job at once.

WHAT HAPPENS WHEN A JOB IS DONE

  - Settings › General › When a job is done › Source: Keep, Move to
    Trash, Move to folder (with a folder you choose), or Delete. Add job
    has the same choice under Output ("After the job"), filled in from
    Settings; each job keeps its own choice, and Rescan reuses the one
    from the last Add job. Jobs from earlier versions keep their source.
  - The source is the game folder, the archive with every part of its
    set, or the container file, and a patch the job integrated. The app
    acts on a job that is Done and whose output is on the disk. A .pkg
    whose checklist reported failures keeps its source. A failed or
    stopped job never touches it.
  - A job checks its output when it is due, not every job at the start:
    before its archive is unpacked when the game can be read from it,
    otherwise right after. When the output is already there and the job
    moves, trashes or deletes its source, it does that and the job is
    Done ("Its output was already there; the source was moved to …").
    A job that keeps its source is Skipped, as before; so is one whose
    source another queued job still needs. With Ask, the one question
    still comes at the start. Rescan with a clean-up chosen also queues
    games already in the output folder, so their sources get cleaned up.
  - "Already there" means same title, version and format. When the job
    knows the firmware its output needs, a file with another firmware
    tag is another build and does not count (one from before firmware
    tags does). For an archive the firmware is known only after
    unpacking, so the tag does not count then, except that a backport
    job wants a file at or below its target.
  - It never touches a source that is or holds the job's output, sits
    in the same folder as the output (a .ffpfsc next to the .pkg built
    from it: both stay), a whole drive, the home folder, the app's own
    temp and profile folders, or a source another job in the queue
    still needs (the last of those jobs takes care of it).
  - The game's folder goes whole. When the source sits in a folder named
    after the game (its title id, the archive set's name or its title)
    that holds no other game, Move and Trash take that folder with
    everything in it, notes and pictures included. Two games in one
    folder are handled apart: each job takes its own files, and the last
    one takes the folder once only its game is left in it. Delete removes
    the game's files, and the folder only when nothing but notes,
    checksums or pictures is left in it.
  - No empty folders are left behind: a folder emptied by the action is
    removed, and its parent too while that is empty. Never removed or
    moved whole: the folder a job was added from (Add job, Rescan), a
    drive, the home folder and its standard folders, the output and the
    destination folder.
  - Move to Trash uses the Trash of the source's drive, so Put Back in
    Finder restores it. Move to folder renames on the same drive and
    copies, checks and then removes across drives; the queue waits for
    the move, so the copy does not share the drive with the next job. A
    name already taken in the folder gets a number, the same one for
    every part of an archive set. Choosing Delete in Settings asks once.
  - Notify: Off, Each job, or Queue end, as a banner in Notification
    Center.
  - When the queue is done: Nothing, Sleep, or Quit, only after the last
    job of a run, not after Stop. Sleep and Quit wait 30 seconds in a
    small window with Cancel; a new run closes it.
  - The finished-job checkboxes (show the result, remove from the queue,
    open the output folder, sounds) moved into the same section.

SEVERAL JOBS AT ONCE

  - Command-click (Ctrl-click on Windows) adds a job to the selection or
    drops it, Shift-click selects a range, Command-A selects every job,
    Escape keeps only the one in focus. Remove, the Delete key and the
    right-click menu ("Remove 3 jobs") act on all of them; the running
    job stays. Removing several jobs that keep extracted copies asks
    first, like Clear does.
  - The details pane shows "3 jobs selected" with their size, how many
    are queued, done or failed, and Remove.
  - The selection follows its jobs while the queue changes underneath,
    for example when a job is added or one finishes.

INTEGRATE A PATCH: BACKPORT FILES, AND THE ORIGINALS ARE KEPT

  - Ready-made backport files (a .zip or .rar with a patched eboot.bin,
    modules, fakelib/ and param.json in one folder) go in through
    Integrate a patch. When the patch brings its own AMPR emulator
    (fakelib/libSceAmpr.sprx), the game's old ampr_emu.index is taken
    out, and a .pkg gets no new one: that emulator builds its index
    itself. A README, checksums or .nfo beside the patch's files stay
    out of the game.
  - Every file the patch replaces or takes out is kept: a folder
    "Original files - <patch name>" next to the built file holds them
    at their path in the game, with a README that names the patch and
    lists what was replaced, removed and added, so the unpatched game
    can be put back together. The folder appears when the job is done;
    a failed or stopped job leaves nothing.
  - A patch for another game is refused, in Add job when both games
    can be read, and when the job runs. A backport made for another
    version of the game gets a warning.
  - A .rar patch's eboot.bin is read for the firmware tag too. While a
    patch's firmware is unknown, only a file with exactly the job's
    name counts as its output already being there, so a backport is
    never mistaken for the build that is there already.
  - Fixed: with the temp folder on an exFAT drive, a patch from a .zip
    or .rar was copied into the game as a whole folder, and the job
    failed with "Multiple game folders/files found". macOS puts a
    "._<folder>" file beside a folder unpacked there, and that file was
    taken for the patch's content. Such files no longer count, and a
    patch whose files sit beside other folders is refused with the
    reason instead of being copied in.

OS CLUTTER STAYS OUT, EVERYWHERE

  - macOS and Windows leave files behind that are no part of a game:
    ".DS_Store", "._<name>" AppleDouble files (an exFAT drive gets one for
    every file that carries an attribute), "__MACOSX" folders from zips,
    "Thumbs.db", "desktop.ini" and the like. The app already kept them out
    of every image it packs; now they never travel at all. Every part of
    the app works from one list of these names.
  - Unpacking a .zip skips them; after a .rar or .7z is unpacked they are
    removed before the game is looked at. A folder built into a .pkg is
    cleaned first, and the package tool leaves them out when it stages
    the files. A .ffpfsc or .pkg unpacked to a folder comes out without
    them, and so does a folder copied to temp for a patch.
  - When a job is done, Move to folder leaves them behind: a copy to
    another drive skips them, and a move on the same drive drops them
    from the moved folder. Move to Trash takes the folder as it is.
  - Fixed: unpacking a container to a folder on an exFAT drive could
    fail with "No such file or directory: ._<file>". macOS puts such a
    file beside one the app has just written and takes it away again
    moments later; the app no longer tries to move it into place.

AN ARCHIVE IS READ AGAIN BEFORE ITS JOB RUNS

  - An archive job read its set once, when it was added. A set that was
    still downloading then kept the size of the parts that were there
    (one part of nine, 10 GB instead of 88 GB, unpacked size unknown),
    and the drive placement, the space check and the queue all worked
    with that. Right before the job runs, the app now reads the set
    again when it changed or its unpacked size is still unknown: the
    parts, their size on disk, and the unpacked size from the headers
    (with the saved passwords).
  - A set that cannot be read then, for example because a part is
    still missing, is not unpacked by half: the job fails with the
    reason and the queue goes on. Retry runs it once the set is
    complete.

A COPY KEEPS ITS SOURCE

  - A job with nothing to change (a .pkg to a .pkg, a .ffpfsc to a
    .ffpfsc) became a copy that removed the original after a copy to
    another drive, and renamed it away on the same drive, unless "Keep
    the source" was ticked; that box was off by default. The original
    now stays unless the job's After the job choice says otherwise. On
    the same drive the copy is an APFS clone (instant, no extra space);
    where the drive cannot clone, a real copy that first checks the free
    space. "Keep the source" is gone; After the job covers copies too,
    and Delete there takes the fast way (a rename on the same drive).
  - Organize renames on the same drive and copies across drives, the
    original staying where it was.
  - --copy-mode keep|organize|move replaces --keep-source on the command
    line; keep is the default.

THE LINE UNDER A JOB READS THE SAME FOR EVERY JOB

  - The line under a job's name says what the job started from:
    Archive, Folder or the container's type (.ffpfsc, .pkg, …), then
    the changes and the output. It no longer depends on whether the
    source is still on the disk: a folder moved away after the job read
    as ".000 …" (the end of its name taken for a file type), an
    extraction removed after the job read as "File", and a job that was
    unpacked from an archive switched from Archive to Folder.
  - A job whose game is not read yet shows no package symbol in place
    of the title id; the id appears once the archive has been read and
    the name does not carry it already.

ONE BADGE FOR EVERY JOB THAT WAITS

  - A job whose source is an archive showed a yellow "Waiting" badge
    while every other job waiting for its turn showed a grey "Queued".
    Since the queue extracts an archive when its job comes up, both
    wait the same way; both now show "Queued". Yellow is left to
    "Extracting", when an archive is actually being unpacked.

A COPY SHOWS ITS OWN PROGRESS

  - A job that only copies its source (a .pkg to a .pkg with nothing to
    change, or a copy job) showed 84 % while the copy had just begun,
    with Temp PFS and Compress ticked off although a copy does neither.
    The copy now tells the app what it is: its bar runs from 0 to 100 %
    with the copy, only the steps it takes are shown, and Speed and Left
    show its rate and time left.
  - The text under the step bar no longer flips between two messages
    every 30 seconds, which moved the whole card each time, and it no
    longer says the write "may show 0 %" while its bar moves. The line
    keeps room for two lines, so a shorter text does not move the card.

THE PACKAGE BUILDER MOVES TO LIBPROSPEROPKG BUILD d7090eb6

  - The bundled ffpfsc-pkg-tool, now versioned with the app (2.1.0),
    links the LibProsperoPkg assembly from the fpkg-gui 0.6.11 release
    (1.2.0, build d7090eb6). A source PlayGo set is no longer copied
    into the package: the library keeps its file assignments, chunk
    labels, languages and scenario presentation (up to 255 chunks, 5
    scenarios) and rebuilds the image ranges for the image it just
    made, in the same pass. The validate checklist gained
    "cnt.playgo-layout": the ranges must cover exactly the image before
    the embedded CNT. A stale or damaged source set (unsorted hashes,
    chunk ids past the count, swapped files) is discarded and
    regenerated instead of shipped.
  - The library's inner-image layout pass (outer block coalescing and
    relocation alignment adjustment, "matches the Publishing Tools
    layout pass") is on by default; --layout-pass off gives the layout
    of the 1.1.x builds. The pass only rewrites the image when that
    saves at least 1 MiB and 0.1 %. Three packages built from the retail
    sample with the layout pass off, on, and with a regenerated PlayGo
    set all install and run on the console (2026-10-05, FW 11.60); on
    that sample the pass found 512 KiB to save and left the layout
    alone, so a package it did rewrite has not been on a console yet.
  - drm_type 16 for retail volumes is upstream now. The IL patcher
    checks for it instead of applying it and refuses an older assembly.
    Three patches remain: fakelib/libSceAmpr.sprx and libScePlayGo.sprx
    stay in the package (2), /ampr_emu.index stays in the image at both
    places the new build drops it (3, new), and package reading is
    single-threaded (4, new) because the parallel inner-PFS sessions
    crashed the tool on macOS.
  - No ReadyToRun precompilation: with it, a Kraken build corrupted
    memory about one run in eight on Apple Silicon, none in 48 runs
    without. list-inner got a little faster; the tool binary is 38 MB.
  - Temporary folders reach the library by their real path. The new
    build refuses a path through a symlink, which every /var path on
    macOS is.
  - The end-to-end test accepts what the new build changes on purpose:
    fake-signed SELF headers get the standard magic, playgo-scenario.json
    is written, and package -> folder -> package is a fixed point from
    the second round-trip on when the source set had to be regenerated.

THE LAST SOURCE IS PRE-SELECTED, AND RESCAN FINDS NEW DOWNLOADS

  - Add job opens with the last source already in the field. When the
    field is empty, the folder picker opens where the last source came
    from. The output folder is remembered, and both pickers in Settings
    now open at their current value.
  - A new "Rescan" button in the queue header searches the folder of
    the last Add job for new sources and queues a job for each one that
    is not already here. "Already here" means: its path is in the queue
    or the history, OR a release with the same title id ([PPSA12345])
    is in the queue, is in the history, or already sits in the output
    folder — so a game you downloaded again under the same name is not
    queued twice. The settings of the last Add job (output, backport
    target, format, compression, organize) are reused. Nothing new?
    One line in the log says what was skipped.

TWO-FINGER SCROLL ON MACOS

  - The queue list and the Settings pages scroll with a two-finger
    trackpad swipe. Tk 9, which the app ships with, reports a trackpad
    swipe on macOS as its own event, TouchpadScroll, with pixel deltas,
    and no longer as a mouse-wheel notch. Tk binds that event for text
    boxes and lists on its own, which is why the log scrolled and the
    queue did not; a canvas, which the queue is, gets nothing unless
    the app binds it. The app now does, with Tk's own delta unpacking,
    and the Settings pages (a CustomTkinter scroll frame, which binds
    only the wheel) get the same binding.
  - The queue list scrolls in pixels now, so a slow swipe moves it
    smoothly instead of in four-pixel steps; a wheel notch still moves
    40 px. Linux (Button-4/5) and a sideways swipe are handled too.

EDIT ON A DONE JOB MAKES IT ACTIVE AGAIN

  - A finished job can be edited; saving the changes queues it again
    with the new settings. The output check runs anew, so a changed
    backport target or output format is treated as a fresh run. Until
    now Edit on a Done job was refused.


THE QUEUE KEEPS ITS ORDER, AND YOU SET IT

  - Jobs stay where you added them. A job that finished, failed or was
    skipped used to move to the end of the list, and the next job was
    pulled to the top; now each one only changes its mark. The queue
    works through the jobs that have not run yet from the top down.
  - Drag a job to another place in the list to change what runs when; a
    line shows where it lands. Right-click › Run next moves a job above
    the first one still waiting, and Move up / Move down stay there too.
    The running job can be moved as well; it keeps running.
  - Retry runs that job next without moving it.
  - The queue bar counts by job, so it stays right when you reorder, and
    a job added while the queue runs now counts in "Job n of N".

PROGRESS AND TIME LEFT OVER ALL JOBS

  - While the queue runs, the foot of the queue list shows how far the
    whole run is and about how long it still takes: "All jobs 39 %" on
    the left, "about 54 min left" on the right, with a thin grey bar, so
    blue stays the colour of the running job. The status bar shows the
    same next to "Job 2 of 5", in every view.
  - The share counts each job by its size. The time left uses the pace
    of the jobs this run has finished (seconds per GB) for the gigabytes
    still to do; before the first one is finished it uses the running
    job's pace. It appears after the first minute and a half, in whole
    minutes, and in five-minute steps beyond an hour, because a single
    job's pace changes between unpacking, building and compressing.

AN OUTPUT THAT IS ALREADY THERE IS SKIPPED

  - Start checks which jobs would write a file that is already in the
    output folder, before anything is unpacked or packed, and skips
    them. Until now every job replaced an existing file without a word,
    after hours of work, and a .pkg got a second copy named "(2)".
  - Settings › Interface › "When the output is already there" sets the
    rule: Skip (the default), Ask (one window lists every such job:
    Skip, Overwrite, Keep both or Cancel), Overwrite, or Keep both,
    where the new build gets a numbered name beside the old file:
    "Title (2) [PPSA01234] [v01.000] [fw10.00].ffpfsc", within the
    ShadowMount name limit.
  - The check uses the name the job will give its output. A file with
    the same name but another firmware tag counts as the same output.
  - A job whose name is known only after its archive is unpacked (a
    solid 7z or RAR, a .pkg inside an archive) is checked right after
    the unpack, before the long packing step, and follows the same rule
    (or the answer given at the start). A skipped job leaves the run
    without counting as failed.
  - Overwrite replaces an existing .pkg too, instead of keeping both.

A JOB IS NAMED AFTER ITS GAME

  - The queue shows the game's title and title id, "Example Quest
    [PPSA01234]", as soon as the app can read them:
    from a game folder, a .ffpfs, .ffpfsc, .exfat or .pkg, and from a
    ZIP, RAR or 7z that is not solid, whose param.json is read out of
    the archive alone. A release name like "[site]-PPSA12345.part01"
    says little. For other archives the title appears once the archive
    is unpacked.

ADDING MANY JOBS NO LONGER FREEZES THE WINDOW

  - Add job builds its jobs in the background. Reading the headers of
    a many-part archive on a slow drive takes seconds, and the window
    froze until every source of a folder was read. Now each job joins
    the queue as soon as it is ready, a line with a bar above the list
    counts them ("Adding jobs… 6 of 9"), and a Start pressed meanwhile
    begins once the last one is in.

FINISHED JOBS STAY IN THE QUEUE

  - A job that succeeds stays in the queue, marked Done with a green
    check, below the jobs still to run. It used to vanish the moment it
    finished. Settings › Interface › "Remove a job from the queue when
    it is done" brings that back; failed jobs always stay.
  - Clear completed, in the queue header, removes the finished jobs. A
    right-click on it (or on a job) offers Clear failed, for failed,
    skipped and cancelled jobs, and Clear all. The running job always
    stays, and clearing a job that kept an extracted copy for a retry
    asks first, because the copy goes with it.
  - In a narrow window the header buttons drop their words and keep
    their icons, so the title and Start stay whole.
  - "Game 2/5" counts only the jobs that run, not the finished and
    failed ones listed with them, and Start is off while every job in
    the queue is done. A finished job stays listed after a restart,
    even when its source is gone.

A FAILED JOB CAN BE CHANGED AND RUN AGAIN

  - Edit works on a failed or cancelled job. It used to open on the
    extracted copy the app had just deleted after the failure, and Add
    refused the missing source. The editor now shows the source the job
    will run from: the copy it kept, or the archive it came from.
  - Retry sits next to Edit for a failed, cancelled or skipped job and
    runs that job again, on its own; the other failed jobs stay as they
    are. The error window has Edit job and Retry buttons too, and for a
    refused backport it says what to do: pick another target (Check
    tells you which one works) or add patched libraries for it.
  - A failed job keeps what it extracted from its archive, like a
    cancelled one, so a retry does not unpack the archive again.
    Removing the job deletes the copy. When the next job of a batch
    needs the space, the app deletes the copies of failed jobs first
    and says so in the log; a copy kept after a cancel stays.

A BROKEN ARCHIVE IS NOT A PASSWORD QUESTION

  - A damaged or incomplete archive no longer asks for a password. The
    check that runs when you add an archive read every failure as "none
    of your saved passwords opens it", so a set with a missing or
    corrupt part brought up the password prompt, and the right password
    typed in was refused as well. The check now tells the two apart: it
    asks only when the archive answers with a password error, and
    otherwise names the damage in the log and the details pane, for
    example "1 part of the set is missing (….part2.rar)" or "its data
    is damaged". A damaged ZIP reads as damaged too.
  - When such an archive fails to extract, the error says what is
    broken, and the error window adds that a password does not help.
  - A part that goes away while the archive is extracted (a drive that
    drops out or falls asleep) ends the job with an error. The
    extraction used to wait for that part forever.

A BACKPORT IS CHECKED BEFORE THE GAME IS UNPACKED

  - A backport job on a .pkg, .ffpfs or .ffpfsc reads only the game's
    executables out of it and runs the function check on them before
    it unpacks the whole game. A target that cannot work is refused
    after seconds; it used to be refused after the full unpack, which
    takes half an hour for a big package.
  - Check in Add job reads a .pkg, .ffpfs or .ffpfsc the same way, so
    you see the verdict before you add the job. --backport-analyze
    takes these containers too.

ARCHIVE PASSWORDS

    OK and Skip buttons sat below the bottom of the window.
  - The prompt only comes up when none of your saved passwords opens

A CANCELLED JOB KEEPS WHAT IT ALREADY UNPACKED

  - Cancel a job after its archive was extracted, and the extracted
    copy stays. Start runs the job from it again, without unpacking the
    archive a second time; removing the job from the queue deletes it,
    and a successful run cleans it up as before. A job cancelled while
    its archive is still extracting drops the half-done copy, and the
    startup cleanup never offers a copy a queued job still keeps.
  - A job whose extracted copy is gone (after a failed run, a clean-up
    or a restart) starts again at its archive. It used to point at the
    deleted copy and fail, or was parked as "source missing".

PROGRESS YOU CAN SEE WHILE A .PKG IS UNPACKED

  - Unpacking a .pkg (to change it, to build a .ffpfsc from it, or as
    an extract job) shows its progress, speed and time left. The
    helper that unpacks it prints nothing until it is done, so the
    window sat at "Extracting 0 %" for minutes. The helper works in
    three steps, all on the temp drive: it decrypts the package into a
    temp file, unpacks the game image from it into a second temp file
    (as large as the game) and then writes the game files. The backend
    reads the package's file list first and, every second, asks the
    system how many bytes the helper has written in all three steps.
    Counting the folder size instead reached 99 % after the second step
    and then stood still for the whole third one.
  - The progress line says where and which step: "extract the .pkg on
    SAMSUNG, step 3 of 3: write the game files (150.2 of 204.5 GB
    written) @ 170 MB/s ETA 5m".
  - "Temp PFS" moves while MkPFS writes the uncompressed image. MkPFS
    counts whole files, so a game with one 57 GB file showed "0 %
    write" for ten minutes, and the window only said "Large games may
    look frozen here". The backend counts the bytes MkPFS has written
    and shows "write the PFS image on SAMSUNG: 34.0 of 80.9 GB".
  - The space check reads the size of the game out of the package. The
    data in a .pkg is compressed, so a 46 GB package can hold an 81 GB
    game, and unpacking it needs twice the game on the temp drive for a
    moment (the unpacked image and the files side by side). The check
    used the package size and asked for far too little; the Space line
    showed "Temp image ~55 GB" for a job that needed about 170 GB.
  - The log names the folder and the drive a job unpacks to, with the
    free space there, and the details pane has a Drives line: where the
    job works and where it writes.
  - A job that unpacks first (a .pkg or image changed and rebuilt) no
    longer reports 94 % when only the unpack is done. Its bar follows
    the order the job runs in: unpack, changes, build, compress.
  - The job's bar in the queue no longer jumps. The 30-second "still
    working" update and the progress lines computed the percentage in
    two ways, 20 points apart; adding a folder while a job ran set the
    bar to 0 % for a moment. One value feeds the bar now, it never
    moves backward, and messages about other jobs go to the footer.

BACKPORT WITHOUT A LIBRARIES FIELD

  - Add job no longer asks for patched libraries. A backport lowers the
    SDK, and when Check finds functions the target lacks, the job takes
    the set for its target from the patched libraries folder in
    Settings. The field kept coming back after you cleared it, because
    the editor refilled it from Settings and only ever saved a value
    that was not empty.
  - A patched libraries setting that points at the firmware libraries
    folder is cleared at start, with a line in the log: that folder
    holds the original libraries, which never go into fakelib/.

PARENT FOLDERS: EVERY SOURCE IN THEM, ONE JOB EACH

  - Add job takes a folder of sources again. It searches the folder and
    its subfolders for game folders, archives (.zip, .rar, .7z; a
    multi-part RAR set once) and containers (.ffpfs, .ffpfsc, .pkg,
    .exfat, .ffpkg), and queues one job per source with the changes
    and the output you chose. Notes and checksum files, hidden files
    and the app's own temp folders are skipped. In 2.0.0 only unpacked
    game folders counted, so a folder of archives or packages was
    refused as "not a PS5 game folder".
  - In such a batch, a game folder to a folder with nothing to change
    is left out, and Check reads the first game folder.
  - An archive that holds a .pkg is unpacked and converted like any
    other package; it used to stop with "no supported payload".

PREPARE THE PATCHED LIBRARIES IN ONE CLICK

  Settings gets a "Prepare 7.61" and a "Prepare 6.02" button that
  download BestPig's BackPork BPS patches from GitHub, apply them to
  your own 10.01 libraries in the folder above, and write the patched

ERROR DIALOG: PLAIN WORDS, NOT A CHECKLIST

  A failed job used to open a big red "Compression Failed" dialog with
  a six-item "Possible Causes" list that repeated for every job kind,
  so the one line that mattered — e.g. "Permission denied '/Volumes/
  SAMSUNG'" — was pushed below the fold. The dialog now leads with the
  backend's own message, adds a plain-words explanation for the
  shapes we recognise (a drive that dropped from /Volumes, permission
  denied, ENOSPC, EROFS, a wrong archive password, a SIGKILL, a folder
  without eboot.bin), and shows the log condensed to its last lines.

FPKG BUILD: NO STRAY INTERMEDIATES IN THE TEMP FOLDER

  The package tool wrote its inner pfs_image.dat (about the size of the
  package) straight into whatever folder --temp received, so a build
  left a file next to the user's own files on the temp drive; a crashed
  build left it there for good. Every fPKG build now gets its own
  tmpXXXXXXXX subfolder (the same shape mkpfs runs use), the folder is
  removed after the build, and a leftover after a crash is reclaimed
  by the app's startup sweep.

ONE DOOR FOR EVERY JOB

  The seven verb buttons (Pack, Convert, Patch, Sign, fPKG⇢, Browse,
  Organize) are gone. Every job the app can run is the same three
  things, and the new "Add job" dialog asks for exactly those:
    1. Source — a game folder, a parent folder of games, an archive, a
       disk image, a .ffpfs, a .ffpfsc or a .pkg. One line says what
       was detected (kind, title id, version, SDK version). For an
       image or package, "Look inside…" opens the browser: a peek, not
       a job.
    2. Change the content — optional, applied in this order: integrate
       a patch, backport to an older firmware, sign the executables.
       Each shows its options only when checked.
    3. Output — Folder, .ffpfs, .ffpfsc or .pkg, for any source. A
       .pkg shows its retail switches.
  A sentence above the button says what the queue will do ("Backport
  to 7.61, then build .ffpfsc"), and the queue row and the details
  panel carry the same sentence. Same format with nothing to change is
  a copy or move; a folder to a folder with nothing to change is
  refused. Choices are remembered per kind of source, a dropped path
  opens the dialog with it, Enter adds, double-click edits a queued
  job in the same dialog. A parent folder makes one job per game.
  Browse and Organize sit top-right with Settings.

BACKPORT: RUN A GAME ON AN OLDER FIRMWARE

  A new content change lowers the SDK version in eboot.bin and every
  prx/sprx to a published target and copies your own patched system
  libraries into the game's fakelib/ folder. Targets: 7.61 (public
  library patches exist), 6.02 (experimental, a smaller public set),
  10.xx (SDK only, for a game newer than the console). Nothing above
  10.xx is offered: no public SDK values exist for it. No library is
  bundled with the app; you extract them from your own firmware and
  apply the public patches yourself. Two Settings fields hold the
  default folders. "Check" in the dialog reads which functions the
  game imports and compares them with the target firmware's libraries
  and your fakelib, and reports per library whether it is covered,
  before anything is built. Also from the command line:
    --backport-target 7.61 [--backport-libs DIR]   with any build
    --backport-analyze SRC --backport-target 7.61 [--fw-libs-root DIR]

ANY SOURCE TO ANY OUTPUT IN ONE JOB

  The backend gained a chain mode (--to folder|ffpfs|ffpfsc|pkg). A
  container is unpacked into scratch, the changes are applied, and the
  result is packed by the same code as before, so a plain pack is
  byte-for-byte what it was. New in one step: .ffpfsc → change →
  .ffpfsc, .pkg → .ffpfsc, .pkg → change → .pkg, and image → change →
  folder. A folder source is changed in place, as Sign always was; a
  container source is never touched.

fPKG: THE PUBLISHING RULES FOR sce_sys, APPLIED WHILE STAGING

  The builder now checks the sce_sys content against the requirements
  of the official publishing tools and repairs what a damaged dump gets
  wrong. Everything happens in the staging copy; the source is never
  touched, and every change is logged.
    • Presentation images must be 8-bit, non-interlaced PNGs: icon0,
      pic0 and pic1 (and their _NN variants) RGB, pic2 (the foreground
      image shown while the application starts) RGBA, icon0 512×512.
      A readable PNG in another form is converted (RGB flattens
      transparency onto black). One that is no image at all is rebuilt
      from its DDS, or left out with a warning when there is none.
    • A DDS that is not DX10/BC7 or not the size of its PNG (a stale or
      mislabeled file) is generated again from the PNG.
    • A PlayGo set that does not describe the packed files — its hash
      table lists other paths, or its file map covers another count —
      is rebuilt; the builder used to keep any well-formed set as it
      was. A set that matches is kept.
    • A title without an applicationDrmType (also a generated
      param.json) becomes "standard"; it now gets the debug license too,
      so it no longer shows a padlock.
    • A param.json that is not JSON stops the build: the builder would
      otherwise write a generic one and lose the title's settings. An
      empty eboot.bin stops it too; an empty module gets a warning.
  Repaired images carry no time stamps, so deterministic builds stay
  byte-identical.

fPKG: A LONGER VALIDATE CHECKLIST

  After every build the checklist now also covers: each presentation
  image and its DDS (a missing or broken icon0.dds is a failure — such a
  package installs but never starts), both license entries for a
  standard or upgradable title, the NP title and binding files, the
  snd0.at9 format, the default-language title, the contentVersion and
  masterVersion formats, the required system software, and a truncated
  eboot.bin.

fPKG: UNPACKING A PACKAGE GIVES THE WHOLE sce_sys BACK

  A package keeps most sce_sys files in its metadata table, not in the
  file image. Unpacking lifted only ten of them; the DDS images, pic2,
  sound, trophy and uds data, nptitle and the license were lost. Now
  every named metadata entry comes back, in the full extract, the
  selective extract and the listing. Only the package's own bookkeeping
  entries stay out.

fPKG: PACKAGE → FOLDER → PACKAGE IS A FIXED POINT

  A deterministic build of an unpacked package gives the same bytes as
  the package. For that, the AMPR emulator index is written over the
  files as the package presents them: param.json after the builder's
  own rewrite, and without the files the builder creates at package
  time (PlayGo set, license) or never packs (ext_info.dat).

MORE

  --param-report also shows each title's required system software and
  SDK version. A version taken from masterVersion ("01.03") is written
  as a content version ("01.003.000"), and a title passed on the
  command line is cleaned of control characters and stray spaces.

fPKG: THE AMPR EMULATOR INDEX MATCHES THE PACKED FILES

RETAIL-PERFECT fPKG BUILDS OUT OF THE BOX

  After byte-comparing retail reference packages against the HomebrewTest
  build, and cross-referencing the SvenGDK LibProsperoPkg ps5-pkg-format
  spec, two more defaults were misaligned for retail content. Both are
  now fixed in ffpfsc-pkg-tool with safe fallbacks:

  • AUTO-FAKE-SIGN raw ELFs in the source (default ON).
    LibProsperoPkg's own ProsperoFself.MakeFself converts each raw ELF
    (eboot.bin, *.elf, *.prx, *.sprx) to a fake-self before packing.
    Idempotent — already-SELF files and non-ELF files are skipped.
    Original source folder is never modified: a hardlink mirror of the
    source is created in --temp-dir, only the ELFs to convert are
    unlinked and rewritten in the mirror, and the mirror is deleted
    after the build. Opt out with the new --no-fake-sign flag if the
    source ships pre-signed and you want exact byte-preservation.

    Why this matters: retail game dumps carry unsigned ELFs. A PS5's
    debug-image loader kills any package whose eboot is not fake-self
    (short fan-spin, then CE-100096-6). Users had to run the separate
    🖊 Sign job before Pack; now the builder handles it in-process.

  • AUTO-DETECT PlayGoChunkCount from the source's sce_sys/playgo-chunk.dat.
    If the source (a real game dump) declares a specific chunk count in
    its own PlayGo table, the builder now respects that instead of
    forcing the 1-chunk default set for HomebrewTest-scale content.
    The --playgo-chunks N override still wins if the user pins it.

    Log lines make the choice visible:
        [playgo] source declares 5 chunk(s); using that (was default 1)
        [sign]   fake-signed 6 ELF(s); skipped 2 (already-SELF, non-ELF, or errors)

  • Single unified staging pass. The DDS-icon generation from 1.1.7,
    the new fake-sign pass, and any future source pre-processing all
    share ONE mirror in --temp-dir instead of stacking them, so a
    100 GB game gets exactly one hardlink walk rather than N.

  Verified: 92/92 pipeline tests pass, HomebrewTest builds byte-identically
  to 1.1.10 (nothing regressed on a small homebrew whose eboot is already
  fake-signed). Retail acceptance on the console followed in 1.1.12.

  • LICENSE, NOTICES.md and the license texts of MkPFS and UnRAR were added
    to the repository with this version (LibProsperoPkg's shipped since 1.1.1).

fPKG BUILDS FINALLY LAUNCH ON 11.60 (kstuff-lite 1.13+)

  • Root cause found: LibProsperoPkg 1.2.0's built-in Kraken encoder
    produces byte-identical output to Sony's Publishing Tools DLL — no

    PFS. The PS5 debug loader accepts only the plaintext-no-auth mode

    mode for debug images. Ours didn't — validated structurally,
    extract-inner worked, but the console rejected it at launch with
    CE-100096-6.

    Program.cs now sets ProsperoPublisherImageMode.PlaintextNoAuth and
    PlayGoChunkCount = 1 (Sony's default; LibProsperoPkg's was 64).
    Both fixes verified against a libScePubTools.dll reference build:
    inner PFS byte-identical; outer PFS wrap differs only in harmless
    timestamp/ICV bytes.

  • pfs-dump (scratch tool, not shipped): opens a fPKG, decrypts the
    outer PFS, dumps three layers (A = outer decrypted, B = stored
    pfs_image.dat, C = fully NAPS-decompressed inner PFS) so future
    debugging can byte-diff a builder's output against a reference at
    each level of the container.

  • --playgo-chunks NEW build flag (integer 1..255) — overrides the
    new default of 1 for advanced PlayGo layouts.

  • Firmware note in the Pack dialog, the fPKG-tool README and the
    top-level README updated: no more "≤ 11.40 only". The ceiling on
    any given firmware is the jailbreak stack, not the builder.

  • Verified on-console 2026-09-24: retail PS5 on FW 11.60 with
    kstuff-lite 1.13-dr-test3 launches the HomebrewTest fPKG built by
    this tool.

    after the folder ("convert [PPSA00003] [01.003].ffpfsc"). With
    auto-organize off, such a job now writes to the chosen output folder;
    mirroring elsewhere (a library drive) is unchanged.

  • AMPR: GAMES THAT SHIP THEIR OWN EMU FILES ARE RECOGNISED
    A PlayGo release that already carries fakelib/libSceAmpr.sprx +
    libScePlayGo.sprx (and usually ampr_emu.index) no longer triggers the
    "AMPR emu folder not set" prompt: nothing is asked, nothing injected;
    a shipped index is kept as-is (it belongs to those .sprx), a missing
    one is built. Only one of the two shipped → the emu folder supplies the
    other. Fake-sign-before-pack is skipped (WARN) for a DIRECT folder that
    ships an index — signing would make it stale, and we never rewrite your
    library.

  • GUI driver: 74 checks (auto-organize names for folder / image / fPKG,
    pkg rename, title cleanup, mirror guard, dialog checkbox, snapshot,
    AMPR shipped-files detection).

fPKG IS THE PACK DIALOG'S THIRD FORMAT — ANY SOURCE → .pkg

  • ONE DOOR
      The Pack dialog's format switch became a three-way choice:
      .ffpfsc (compressed) | .ffpfs (uncompressed) | .pkg (fPKG). Picking
      .pkg unfolds the fPKG block (identity + inner codec / Kraken backend /
      level) below the format row; the dialog grows to 700x840 and shrinks
      back when you switch away. The separate "⇢fPKG" button and the
      Build-fPKG dialog are gone; the Converter's "Build fPKG" step and a
      double-click on a queued fPKG job open the Pack dialog with .pkg
      pre-selected.

  • THE INPUT NO LONGER MATTERS
      With .pkg selected every pack source becomes an fPKG job: a game
      folder, a parent folder (scanned — each game its own .pkg), a library
      of bundles (folder mirrored, DLC extras copied next to the .pkg), a
      third-party archive (extracted on its turn, multi-game archives included),
      a .exfat/.ffpkg disk image, a .ffpfs — and a .ffpfsc, which the other
      two formats refuse because it is already packed. The queue snapshot
      that used to stamp compressed/uncompressed onto a fresh pack item now
      turns it into an fPKG job when .pkg is the remembered format — so a
      dropped or browsed source follows the last chosen format, as before.

  • IDENTITY: param.json DECIDES  (fixes a real 1.1.0 defect)
      The bundled tool stamps the header with --content-id as given and
      never reconciles it with sce_sys/param.json; the image→fPKG path
      guessed "UP9000-<TID>_00-PROSPERO00000000", so every real game image
      produced a package whose header disagreed with its own param.json
      ("[FAIL] param.contentId ... != CNT header" in validate). Now the
      backend reads param.json of the resolved source (folder, unwrapped
      image, extracted archive alike) and takes content id, title id,
      version and title from there; --content-id & co. are fallbacks for
      what it lacks and are no longer required. A disagreeing argument is
      logged as a WARN and ignored. The dialog pre-fills the identity from
      param.json for a game folder (dropped again when the source changes)
      and leaves it empty — "auto" — for archives and images.

  • ALSO
      fPKG jobs skip the AMPR/APR emu injection (a .pkg installs natively);
      an fPKG job survives archive extraction as an fPKG job (the payload
      copy used to reset it to pack/unpack); the extra games of a multi-game
      archive become fPKG jobs sharing the compression settings only (never
      the first game's identity); a scan-detected patch is dropped with a
      WARN when a bundle becomes an fPKG job (the builder has no patch
      overlay); bundle sub-folders apply to .pkg output and bundle extras
      are copied next to it; identity typed for an archive source rides
      along as the fallback; editing pack ↔ fPKG on the same source converts
      in place (bundle tags, archive password and queue position survive);
      the space gate lets fPKG extract through and sizes a .ffpfsc source
      at 2x for the unwrap; the remembered fPKG compression (inner/backend/
      speed) persists as fpkg_defaults, the remembered format as
      output_format (the old output_compressed bool stays in sync for the
      pack pipeline).

  • THE fPKG TOOL: 53 MB → 25 MB, SAME SPEED
      backend/native/ffpfsc-pkg-tool is rebuilt without Magick.NET and with
      the .NET runtime trimmed. LibProsperoPkg only references ImageMagick
      for icon conversion; none of our code paths (build in all three
      codec layers, extract, validate, deterministic build) ever load it —
      the 57-check harness passes without it, and it was 28 MB of the file.
      Measured on 240 MB of mixed data the slim JIT build runs at the same
      throughput as before (34 vs 33 MB/s). NativeAOT variants were tried
      too (16-18 MB) and rejected: 10-23 % slower on the Kraken/AES path.
      The wrapper's source (Program.cs, PkgTool.csproj, build README) now
      lives in backend/native/src/ffpfsc-pkg-tool/ — it existed only in a
      temp folder before, and GPL-3 wants it next to the binary. The first
      fPKG attempt's leftovers (prospero.py, libprosperopkg.dylib/.h,
      patches/) are deleted; nothing used them and they shipped as 7 MB of
      dead weight in the app.

  • TWO 1.1.0 CLAIMS CORRECTED (measured, not assumed)
      "Inner codec none = files stored raw" was wrong: the tool Kraken-packs
      every file in every mode (a compressible 8 MB file came out as 1.2 MB
      with 'none'; only incompressible data is stored). --mode adds a codec
      LAYER over the whole inner image; on already-packed data all three
      layers gave the same package size. Texts in the dialog, README, CLI
      help and fpkg.py say so now.
      "Level 0-9" was a placebo: the level reaches the encoder (the log
      says so), but 0..9 produce byte-identical output; only -4..-1 switch
      to a faster, slightly weaker preset (40 MB mixed data: about a quarter
      less time, ~8 % larger). The slider is gone; the dialog offers
      "Kraken speed: normal | fast" (level 7 / -4). The tuning-bar note for
      an fPKG job says none of its controls apply.

  • TESTS
      CLI harness: +1 test, 6 checks (param.json beats a disagreeing
      --content-id and validate stays green; ids omitted → builds; no
      param.json and no ids → readable refusal) — 57/57. GUI driver
      rewritten for the unified dialog: pre-fill, optional identity for
      images/archives, add via the shared classifier, edit, pack↔fPKG
      switch, archive placeholder kept as fPKG, remembered-format drop,
      dialog sizing — 40/40.

    Inner codec         none (safest, largest) / zlib / kraken.
    Content ID / Title  filled from sce_sys/param.json if present, else
                         asked for in the dialog.

  ROUND-TRIP VERIFIED locally on the HomebrewTest sample: build then
  extract-inner returns every source file byte-identical (fake-sign
  transforms eboot.bin as expected). On-console install is the user's
  test and depends on kstuff-fpkg support on his firmware.

  BACKEND CLI

    backend/cli.py picked up matching flags so the app and shell users
    both hit the same code path:

      --fpkg-extract PKG               (with OUTPUT = target folder)
      --fpkg-build   SRC-DIR           (with OUTPUT = folder for the .pkg)
        --content-id, --title-id, --fpkg-title, --fpkg-version
        --fpkg-inner {none,zlib,kraken}
        --fpkg-kraken-backend {automatic,builtin,publishingtools,uncompressed}
        --fpkg-pubtools-dll PATH

  RACE FIX applied at our layer

    LibProsperoPkg 1.2.0's outer-PFS worker crashes with SIGSEGV in
    ProsperoOuterPfsSignature.BlockSector when its build path runs
    encryption across multiple threads. Our wrapper forces
    KrakenMaxDegreeOfParallelism = 1 (also gates the outer-PFS pool)
    so 8/8 test runs succeed instead of 4/8.
